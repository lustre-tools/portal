# Portal

A small web portal that puts Lustre development tools in front of a
browser, so they are usable by people who would rather not install a
Python toolchain to look at a patch series.

It ships with one tool and can host more:

- **Gerrit Change Graph** — an interactive DAG of a patch series.
  Give it a change number, a Gerrit URL or a ticket (`LU-12345`) and it
  renders the whole topology: dependencies, branches, abandoned forks,
  stale patchsets, review state and CI results. Graphs are saved, can be
  labelled and searched, and can refresh themselves on a schedule.
- **Gerrit Dashboard** — optional, embedded from
  [llm_code_and_review_tools][tools]. A per-user attention board of
  what is waiting on you.

Graphs are generated by the `gc` CLI from [llm_code_and_review_tools][tools],
which the installer pulls in as a pinned submodule.

[tools]: https://github.com/lustre-tools/llm_code_and_review_tools

## Install

```bash
git clone https://github.com/lustre-tools/portal.git
cd portal
sudo ./install.sh
```

The installer asks where things should live, what your Gerrit is, and
what the first account should be; then it creates a service user, a
venv, a systemd unit, a timer for scheduled refreshes and an nginx site,
and starts everything. It is safe to re-run — it updates in place.

```bash
./install.sh --dry-run     # print every action, take none
./install.sh --dev         # a local venv only, nothing system-wide
./install.sh --uninstall   # remove units and site; leaves your data alone
```

To try it without touching the system:

```bash
./install.sh --dev
.venv/bin/portal-users set-password --user admin
.venv/bin/portal-users add-role --user admin --role admin
.venv/bin/portal
```

Then open <http://127.0.0.1:5000/>.

Requires Python 3.11 or newer. The site sits behind nginx, which the
installer configures; it binds loopback and does not terminate TLS
itself.

## How access works

Anyone can browse graphs of the **public project** without an account.
Signing in adds the ability to create, re-run, rename and delete them.

Accounts carry roles:

| Role | What it adds |
|---|---|
| *(none)* | create, re-run, edit and delete graphs of the public project |
| `internal` | the same, for every other project — and those graphs become visible at all |
| `admin` | schedule automatic refreshes; implies `internal` |

Which project counts as public is one setting, `PORTAL_PUBLIC_PROJECT`.
Everything else is "internal": hidden from the list, hidden from
autocomplete, and a 404 by direct URL — the same 404 you get for a graph
that does not exist, so the difference cannot be probed.

```bash
portal-users list
portal-users set-password --user alice        # prompts; never takes it as an argument
portal-users add-role --user alice --role admin
portal-users remove-role --user alice --role internal
portal-users delete --user alice
```

Roles are read on every request, so revoking one takes effect
immediately rather than at the user's next login.

## Gating your own services

The portal exposes `/_authcheck?role=<role>`, which answers a bare 200
or 401. That is exactly what nginx's `auth_request` wants, so you can
put any other service behind this login without the portal knowing
anything about it:

```nginx
location /internal-thing/ {
    auth_request /_authcheck?role=internal;
    error_page 401 = @portal_login;
    proxy_pass http://127.0.0.1:9000/;
}

location @portal_login {
    return 302 /login?next=$request_uri;
}
```

Roles are free-form, so `--role wiki` and `?role=wiki` work without
changing any code.

There is also an optional built-in private area: set
`PORTAL_PRIVATE_PREFIX` and it mounts a role-gated file listing there.
Leave it unset — the default — and the portal has no such area at all.

## Configuration

Everything comes from the environment, via `/etc/portal/portal.env`.
[`.env.example`](.env.example) documents every setting; the common ones:

| Variable | Default | |
|---|---|---|
| `PORTAL_SECRET_KEY` | — | **required**; signs the session cookie |
| `PORTAL_SITE_NAME` | `Lustre Tools` | shown in the header |
| `PORTAL_DATA_DIR` | `./data` | graphs, index and accounts |
| `PORTAL_PUBLIC_PROJECT` | `fs/lustre-release` | what anyone may graph |
| `GERRIT_URL` | `https://review.whamcloud.com` | |
| `GERRIT_USER` / `GERRIT_PASS` | unset | an HTTP password from Gerrit's settings, not an account password. Leave blank to query anonymously |

`GERRIT_*` deliberately keep their unprefixed names so one env file can
serve the portal, `gerrit-cli` and `gerrit-dashboard` together.

## Operating it

```bash
systemctl status portal.service
journalctl -u portal.service -f

systemctl list-timers portal-refresh.timer   # scheduled refreshes
portal-refresh --dry-run                     # what is due right now
```

Upgrading:

```bash
git pull && git submodule update --init vendor/llm_tools
sudo ./install.sh
```

## Security

Sessions are signed cookies, `HttpOnly`, `SameSite=Strict`, `Secure`,
and they expire. State-changing requests carry a CSRF token. The nginx
site sets its own security headers rather than inheriting them, and rate
limits the login endpoint. Services run as a non-root user under
`ProtectSystem=strict` with a single writable directory.

Please report anything you find privately — see [SECURITY.md](SECURITY.md).
